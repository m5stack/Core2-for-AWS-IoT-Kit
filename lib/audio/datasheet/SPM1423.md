# Firmware Implementation Specification: Knowles SPM1423HM4H-B Digital PDM Microphone

Source: `SPM1423.pdf`, Knowles SPM1423HM4H-B specification Revision A,
February 16, 2012.

This specification is derived from the provided device specification and is intended to be a self-contained firmware implementation reference for generating a correct driver, HAL integration layer, BSP support, and automated test logic for the SPM1423HM4H-B digital microphone. 

## 1. Purpose

This document is a self-contained firmware implementation reference for the Knowles SPM1423HM4H-B digital microphone.

It is written to enable automatic driver generation, HAL integration, BSP generation, interface validation, and test harness development without requiring the original source document.

This device is not a register-programmable peripheral. It is a digital PDM microphone with a clocked single-bit output interface and pin-selected channel behavior. Therefore, sections related to register maps, register bitfields, command opcodes, and programmable configuration are omitted because the device specification provides no such interface.

## 2. Device Overview

### 2.1 Device Function

The SPM1423HM4H-B is a digital SiSonic microphone with a pulse-density modulated digital output.

### 2.2 Intended Application Class

* Consumer electronics
* Audio capture front ends
* DSP/MCU audio input subsystems
* Multi-microphone PDM input designs

### 2.3 Major Capabilities

* Digital PDM audio output
* Omni-directional microphone response
* Left/right channel style output selection using the `SELECT` pin
* Sleep mode entered by lowering the external clock
* Fast wakeup from sleep when the clock is restored
* Direct connection to a DSP/MCU PDM clock and data input

### 2.4 Software-Relevant Functional Subsystems

* MEMS microphone acoustic transducer
* Internal PDM modulator
* Clocked digital output stage
* Power/sleep state logic
* Channel select logic controlled by `SELECT`

## 3. Communication Interfaces

## 3.1 Primary Digital Interface

The device uses a synchronous digital PDM audio interface.

Signals:

| Pin | Name          | Function             |
| --: | ------------- | -------------------- |
|   1 | `GND`         | Ground               |
|   2 | `SELECT`      | Channel select input |
|   3 | `GND`         | Ground               |
|   4 | `CLOCK (CLK)` | Input clock          |
|   5 | `DATA`        | PDM data output      |
|   6 | `POWER (VDD)` | Supply               |

### 3.2 Interface Characteristics

* Interface type: clocked single-bit PDM output
* Host-provided clock: yes
* Device output: single data line
* Output format: `1/2 Cycle PDM`
* Clock frequency range: `1.0 MHz` to `3.25 MHz`
* Sleep-entry condition: `fclock < 1 kHz`
* Wake condition: `fclock ≥ 1 MHz`
* Maximum output load: `100 pF`

### 3.3 Channel Selection / Edge Ownership

The microphone uses the `SELECT` pin to determine on which clock edge it drives valid data and on which edge it releases the line.

| Label    | `SELECT` level | Drives data after  | High-Z after       |
| -------- | -------------- | ------------------ | ------------------ |
| `Data_H` | High           | Rising clock edge  | Falling clock edge |
| `Data_L` | Low (default)  | Falling clock edge | Rising clock edge  |

This permits two microphones to share a single data line if one is configured as `Data_H` and the other as `Data_L`.

### 3.4 Bus Addressing Rules

This device does not use:

* I2C addressing
* SPI chip select
* UART framing
* CAN identifiers
* USB enumeration
* register address phases

There is no serial control/address bus. Firmware interacts only through:

* `VDD`
* `CLK`
* `DATA`
* `SELECT`

## 5. Communication Protocol

## 5.1 Host-to-Device Model

The host controls the device only through:

* power supply presence
* external clock frequency
* `SELECT` pin logic level

The device returns a continuous single-bit PDM stream when active.

## 5.2 Protocol Behavior

There are no register transactions and no commands.

Protocol behavior is purely signal-based:

* `VDD` applied, `CLK < 1 kHz` → sleep mode
* `VDD` applied, `CLK ≥ 1 MHz` → active mode
* `VDD` removed → powered down mode
* `SELECT = High` → microphone behaves as `Data_H`
* `SELECT = Low` → microphone behaves as `Data_L`

## 5.3 Timing Semantics

For `Data_H`:

* valid data is driven after the rising edge
* output returns high-Z after the falling edge

For `Data_L`:

* valid data is driven after the falling edge
* output returns high-Z after the rising edge

Timing parameters:

* valid-data delay `tdv`: `18 ns` min, `60 ns` max
* high-Z delay `tdz`: `0 ns` min, `16 ns` max

## 5.4 Example Host Operation: Single Microphone

Assume single microphone connected directly to a PDM input:

1. Set `SELECT` to desired polarity, typically low for `Data_L`
2. Apply `VDD` in valid range
3. Drive `CLK` at a frequency between `1.0 MHz` and `3.25 MHz`
4. Wait up to `10 ms` for wake-up if coming from sleep
5. Sample `DATA` on the correct half-cycle using the host PDM peripheral or GPIO capture logic

## 5.5 Example Host Operation: Dual Microphone Shared Data Line

1. Connect both microphones to common `CLK`
2. Connect both microphones to common `DATA`
3. Set one microphone `SELECT = High`
4. Set the other microphone `SELECT = Low`
5. Drive `CLK`
6. Capture rising-edge-owned and falling-edge-owned half-cycles separately in the host

## 10. Data Formats

## 10.1 Primary Output Format

* Format: `1/2 Cycle PDM`
* Signal width: 1 bit
* Stream type: pulse-density modulated audio bitstream
* Output polarity: increasing sound pressure produces a decreasing density of `1`s

## 10.2 Interpretation

The device does not output PCM samples directly. Firmware or hardware must decimate the PDM stream to obtain PCM audio.

## 10.3 Logical Representation

* Bit value meaning is density-based across time, not per-bit amplitude
* Higher acoustic pressure results in lower density of logical `1`s

## 10.4 Byte Order

Not applicable at the microphone interface. The output is a serial 1-bit stream, not byte-framed data.

## 10.5 Signed vs Unsigned Representation

Not applicable at the raw interface. Signedness becomes relevant only after PDM decimation into PCM by host logic/software.

## 12. Operating Modes

The microphone state diagram defines three modes.

## 12.1 Powered Down Mode

Condition:

* `VDD = Off`

Behavior:

* microphone inactive
* no valid output operation

## 12.2 Sleep Mode

Entry condition:

* `VDD = On`
* `fclock < 1 kHz`

Behavior:

* low current mode
* no output
* fast startup path back to active mode

Electrical characteristics in sleep:

* sleep current nominal `25 µA`
* sleep current maximum `45 µA`

## 12.3 Active Mode

Entry condition:

* `VDD = On`
* `fclock ≥ 1 MHz`

Behavior:

* normal operation
* PDM output active on selected half-cycle

## 12.4 Mode Transitions

| From         | To           | Condition                    |
| ------------ | ------------ | ---------------------------- |
| Powered Down | Sleep        | `VDD = On`, `fclock < 1 kHz` |
| Powered Down | Active       | `VDD = On`, `fclock ≥ 1 MHz` |
| Sleep        | Powered Down | `VDD = Off`                  |
| Sleep        | Active       | `VDD = On`, `fclock ≥ 1 MHz` |
| Active       | Powered Down | `VDD = Off`                  |
| Active       | Sleep        | `VDD = On`, `fclock < 1 kHz` |

## 13. Reset Behavior

There is no software reset command.

### 13.1 Effective Reset Mechanism

The only reset-like mechanism is removal and reapplication of `VDD`.

### 13.2 Reset-Equivalent Conditions

* `VDD = Off` places the device in powered down mode
* reapplying `VDD` with `CLK < 1 kHz` enters sleep mode
* reapplying `VDD` with `CLK ≥ 1 MHz` enters active mode

### 13.3 Reset Timing

No explicit power-on-reset timing value is provided. For conservative driver behavior:

* after asserting a valid active clock, allow up to the specified wake-up time of `10 ms` before relying on output validity if coming from a non-active state

## 16. Operational Sequences

## 16.1 Initialization Sequence

1. Ensure `VDD` is within `1.6 V` to `3.6 V`
2. Set `SELECT` to required channel role
3. Drive `CLK` within `1.0 MHz` to `3.25 MHz`
4. Wait up to `10 ms` for active-mode readiness if transitioning from sleep
5. Begin capturing the PDM bitstream

## 16.2 Enter Sleep

1. Keep `VDD` on
2. Reduce `CLK` to `< 1 kHz`
3. Wait up to `10 ms`
4. Treat microphone output as inactive / not valid for normal capture

## 16.3 Exit Sleep

1. Keep `VDD` on
2. Increase `CLK` to `≥ 1 MHz` and within valid operating range
3. Wait up to `10 ms`
4. Resume PDM capture

## 16.4 Power Down

1. Stop use of captured data
2. Remove `VDD`

## 16.5 Reactivate from Powered Down

1. Apply `VDD`
2. Set `SELECT`
3. Provide `CLK`
4. If clock is already active-range, allow up to `10 ms` before assuming full validity

## 17. Driver Initialization Sequence

Recommended startup sequence for generated driver code:

1. Configure host GPIO/peripheral connections for:

   * microphone clock output
   * microphone data input
   * optional `SELECT` control GPIO
2. Assert desired `SELECT` level:

   * low for `Data_L` default behavior
   * high for `Data_H`
3. Enable microphone supply rail, ensuring `1.6 V ≤ VDD ≤ 3.6 V`
4. Start `CLK` at a valid active frequency in the range `1.0 MHz` to `3.25 MHz`
5. Ensure clock duty cycle remains within `40%` to `60%`
6. Ensure clock rise/fall times do not exceed `10 ns`
7. Wait `10 ms` maximum startup/wake budget
8. Start PDM reception and decimation
9. Validate that the data stream is non-stuck and statistically plausible

---

## 18. Runtime Operation Sequences

## 18.1 Reading Audio Data

1. Keep supply stable
2. Keep `CLK` running in active range
3. Capture PDM stream continuously
4. Decimate PDM to PCM in hardware or software
5. Apply downstream filtering/gain in host processing only

## 18.2 Switching Between Shared-Bus Microphones

If two microphones share a data line:

1. Configure one as `Data_H`
2. Configure the other as `Data_L`
3. Keep both on the same clock
4. Use a host interface that separates data on the corresponding half-cycles

## 18.3 Entering Low Power

1. Lower clock below `1 kHz`
2. Wait up to `10 ms`
3. Disable host PDM processing or ignore incoming line state

## 18.4 Resuming from Low Power

1. Raise clock to at least `1 MHz`
2. Wait up to `10 ms`
3. Resume PDM capture and decimation

## 19. Driver State Model

A correct driver should track at least:

* configured `SELECT` role: `Data_L` or `Data_H`
* current intended power state:

  * powered down
  * sleep
  * active
* current clock frequency
* whether wake delay has elapsed
* whether the host capture path is synchronized and receiving plausible PDM data
* whether the design is single-microphone or dual-microphone shared-data-line

Suggested software state enum:

* `MIC_STATE_POWERED_DOWN`
* `MIC_STATE_SLEEP`
* `MIC_STATE_ACTIVE`

Suggested channel enum:

* `MIC_CHANNEL_DATA_L`
* `MIC_CHANNEL_DATA_H`

## 20. Required Safety and Correctness Rules for Code Generation

1. Never drive the microphone pins beyond absolute maximum ratings.
2. Keep `VDD` within `1.6 V` to `3.6 V` during normal operation.
3. Keep `CLK` within `1.0 MHz` to `3.25 MHz` during active capture.
4. Do not assume valid active output immediately after changing from sleep to active; allow up to `10 ms`.
5. Do not assume sleep current immediately after reducing the clock below `1 kHz`; allow up to `10 ms`.
6. Respect `SELECT` polarity exactly:

   * high selects `Data_H`
   * low selects `Data_L`
7. Sample the data line according to the correct half-cycle ownership.
8. In shared-data-line designs, never configure both microphones to the same `SELECT` role.
9. Ensure input capacitance/loading presented to the data pin does not exceed `100 pF`.
10. Maintain clock duty cycle between `40%` and `60%`.
11. Maintain clock rise time and fall time at or below `10 ns`.
12. Treat the interface as a raw PDM stream, not as PCM or register-framed serial data.
13. Use the correct polarity interpretation: increasing sound pressure decreases density of `1`s.
14. Do not generate code that attempts register reads, register writes, command sends, or device-ID queries.
15. Validate stream plausibility in software because no status register exists.
16. When the device is in sleep or powered down, treat data as unavailable.
17. Do not short the data output in normal operation even though absolute maximum short-circuit survivability is specified.
18. Do not rely on unspecified startup timing beyond the explicit `10 ms` wake timing.
19. Do not exceed the maximum clock or voltage limits during test or bring-up.
20. Design BSP power sequencing so that host clocking and capture do not violate the microphone’s mode transition rules.

## 25. Final Implementation Intent

A generated driver for this device should behave as a thin hardware-interface layer for a non-register PDM microphone.

It should:

* manage supply/clock/select sequencing
* represent the microphone state correctly
* capture the raw PDM stream correctly
* honor edge ownership based on `SELECT`
* apply required timing delays for sleep and wake transitions
* avoid any attempt to use register-based control models

Common implementation mistakes to avoid:

* treating the device like I2C or SPI register hardware
* attempting device ID reads
* sampling on the wrong half-cycle
* configuring both microphones identically on a shared data line
* failing to wait for wake-up after restoring active clock
* decoding the raw stream as PCM bytes
* ignoring the inverted density polarity relationship
* exceeding the `100 pF` output load limit
* running the clock outside `1.0 MHz` to `3.25 MHz`
* assuming data validity during sleep or powered-down states

### Reliability Test Summary

After reliability tests, sensitivity shall not deviate more than `3 dB` from initial value.

| Test                      | Description                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Thermal shock             | `100 cycles` of air-air thermal shock from `-40°C` to `+125°C` with `15 minute` soaks                                                                   |
| High temperature storage  | `+105°C` environment for `1,000 hours`                                                                                                                  |
| Low temperature storage   | `-40°C` environment for `1,000 hours`                                                                                                                   |
| High temperature bias     | `+105°C` environment while under bias for `1,000 hours`                                                                                                 |
| Temperature/humidity/bias | `+85°C/85% R.H.` environment while under bias for `1,000 hours`                                                                                         |
| Vibration                 | `4 cycles` lasting `12 minutes` from `20` to `2,000 Hz` in X, Y and Z direction with peak acceleration of `20G`                                         |
| ESD                       | `3 discharges` at `+/-8 kV` direct contact to lid when unit is grounded (IEC 61000-4-2) and `3 discharges` at `+/-2 kV` direct contact to I/O pins (MIL 883E, Method 3015.7)        |
| Reflow                    | `5 reflow cycles` with peak temperature of `+260°C` (reliability test condition; production handling still recommends no more than `3 cycles`)          |
| Mechanical shock          | `3 pulses` of `10,000 g` in X, Y and Z direction                                                                                                        |
