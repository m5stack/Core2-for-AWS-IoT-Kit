# FT6336 Family Firmware Driver Implementation Specification

Source: `Ft6336_cn.xlsx`, FocalTech FT6336-family external-register workbook,
revision V1.3, November 12, 2015.

## 1. Purpose

This document is a self-contained firmware implementation reference for the FT6336-family touch controller register interface exposed by the provided register workbook.

It is intended to enable automatic generation of:

* firmware drivers
* HAL integrations
* BSP support code
* communication protocol handlers
* automated test harnesses

This specification consolidates the device-visible register interface, register pages, command values, operating modes, register semantics, gesture-enable map, factory/test access flows, and data access procedures required by software.

---

## 2. Device Overview

FT6336-family is a touch controller with:

* normal/work mode touch reporting
* factory/test mode register page
* up to **2 concurrent touch points**
* gesture-related control registers
* monitor / active / standby / hibernate power modes
* optional factory/test functions for:

  * raw data readout
  * CB data readout
  * channel order readout
  * RS micro-short test
  * auto calibration
  * water-proof / close-mode / sync / SSCG configuration

Software-visible subsystems include:

* touch-point reporting engine
* gesture engine
* power mode controller
* interrupt reporting mode selector
* chip identification/version registers
* factory/test acquisition path
* calibration/test/status control

The register interface is divided into at least two pages:

* **Work Mode page** selected by writing **0x00** to register **0x00**
* **Factory Mode page (TEST0 page 1)** selected by writing **0x40** to register **0x00**

## 3. Communication Interfaces

## 3.1 Host Communication Model

The provided register workbook defines a byte-addressed register interface with single-byte addresses and mixed single-byte / multi-byte data registers.

The workbook defines:

* register addresses
* access permissions
* page-switch method
* streamed data register read procedures
* write-then-read operations for factory data streams

The workbook does **not** specify in the provided material:

* physical bus type
* slave address
* maximum bus clock
* SPI CPOL/CPHA
* UART framing
* pin-level chip select behavior

Software must therefore implement a generic byte-register transport abstraction with:

* register write of 1 byte or more
* register read of 1 byte or more
* write-register-address then repeated read for stream registers where required by platform transport

## 3.2 Register Page Selection

### Work Mode page select

* Write **0x00** to register **0x00**

### Factory Mode page select

* Write **0x40** to register **0x00**

### Observed behavior

* In work mode, register **0x00** read value is documented as **0**
* Writing **0x40** to **0x00** switches to factory mode

## 4. Device Addressing and Identification

## 4.1 Page/Register Addressing

Registers are addressed by 8-bit register address.

Two logical register pages are defined:

* **Work Mode page**
* **Factory Mode page (TEST0 Page 1)**

The same register address may have different meaning across pages.

### Chip type / product decoding

#### `ID_G_CIPHER_LOW` at `0xA0`

* `0x00` = **Ft6236G**
* `0x01` = **Ft6336G**
* `0x02` = **Ft6336U**
* `0x03` = **Ft6426**

#### `Chip_Type` at factory `0x2F`

* `0x00` = **Ft6236G**
* `0x01` = **Ft6336G**
* `0x02` = **Ft6336U**
* `0x03` = **Ft6436U**

## 4.3 Device Discovery Procedure

Recommended software discovery:

1. Select **Work Mode** by writing `0x00` to `0x00`.
2. Read:

   * `0xA8` vendor ID
   * `0x9F/0xA0/0xA3` chip code bytes
   * `0xA6` firmware version
3. Optionally read factory `0x2F` after switching to factory page.
4. Validate product family code before enabling advanced features.

## 5. Communication Protocol

## 5.1 General Register Access

The provided material defines a register-oriented protocol:

* write: `register_address <- value`
* read: `read register_address`
* sequential streaming reads for buffer registers in factory mode

## 5.2 Page Switching

### Enter work page

* write `0x00` to register `0x00`

### Enter factory page

* write `0x40` to register `0x00`

## 5.3 Touch Data Read Model

In work mode:

* read `TD_STATUS` at `0x02` to determine number of reported points
* if point 1 present, read registers `0x03`..`0x08`
* if point 2 present, read registers `0x09`..`0x0E`

The workbook defines each coordinate as a high 4-bit field followed by a low
byte. Assemble the 12-bit values as:

```c
point1_x = ( ( P1_XH & 0x0F ) << 8 ) | P1_XL;
point1_y = ( ( P1_YH & 0x0F ) << 8 ) | P1_YL;
point2_x = ( ( P2_XH & 0x0F ) << 8 ) | P2_XL;
point2_y = ( ( P2_YH & 0x0F ) << 8 ) | P2_YL;
```

Bits 7:6 of each `P*_XH` contain the touch event, and bits 7:4 of each
`P*_YH` contain the touch ID, so those bits must not enter the coordinate.
The workbook's `P2_XH` description mistakenly says "point 1" for the high
X-coordinate nibble; the register name and surrounding point-2 register block
make the intended point-2 meaning unambiguous.

## 5.4 Factory Stream Read Model

### Read channel order

1. Write start index to `0x31` (`Channel_Order_addr_R`)
2. Read from `0x37` (`Channel_Order_buf`)
3. Total bytes to read: **(`通道数` + `虚拟按键数`)**
4. Example from source material: `w 37 r X`

### Read Raw Data

1. Write start index to `0x34` (`RawData_addr_R`)
2. Read from `0x35` (`RawData_buf`)
3. One channel = **2 bytes**
4. Read length = **2 * N**, where `N = VA区 + KEY区 通道个数总和`
5. Bytes `2*N` and `(2*N)+1` correspond to **close mode rawdata**
6. Example from source material: `w 35 r X`

### Read CB Data

1. Write start index to `0x33` (`CB_addr_R`)
2. Read from `0x39` (`CB_buf`)
3. One channel = **2 bytes**
4. Read length = **2 * N**, where `N = VA区 + KEY区 通道个数总和`
5. Bytes `2*N` and `(2*N)+1` correspond to **close mode rawdata**
6. Example from source material: `w 39 r X`

### Read RS test data

1. Write start index to `0x34`
2. Read from `0xF4` (`RS_DATA_BUF`)
3. One channel = **2 bytes**
4. Read length = **2 * N**, where `N = VA区 + KEY区 通道个数总和`
5. Bytes `2*N` and `(2*N)+1` correspond to **close mode rawdata**
6. Example from source material: `w F4 r X`

## 5.5 RAWDATA Handshake

Factory `AcmdREG` at `0x08`:

* `0x00`: RAWDATA ready, host may read
* `0x01`..`0xFF`: device may begin preparing next RAWDATA frame

Software should not assume arbitrary streaming readiness without checking `AcmdREG`.

## 8. Reserved Bit Handling

Because the workbook explicitly marks many registers and fields as reserved, generated code must follow these rules:

* reserved registers must not be written unless required by a validated vendor flow
* for partially defined registers, undefined bits must be preserved on read-modify-write
* if a reserved register is read-only, it may be ignored
* if a register is labeled only as `Reserved`, treat it as inaccessible for functional logic
* for registers with only bit 0 or low bits defined, keep all other bits unchanged unless a full register value is explicitly required by a known mode write

## 9. Commands or Opcodes

No separate opcode table is defined; the workbook uses register writes as commands.

| Command                  | Code / Write Sequence               | Parameters | Description                              |
| ------------------------ | ----------------------------------- | ---------- | ---------------------------------------- |
| Select Work Mode Page    | write `0x00` to `0x00`              | none       | Switch register page to normal/work mode |
| Select Factory Mode Page | write `0x40` to `0x00`              | none       | Switch register page to factory mode     |
| Trigger upgrade flow     | write `0xAA`, then `0x55` to `0xBC` | sequence   | Triggers upgrade process                 |
| Enter gesture state      | write `1` to `0xD0`                 | none       | Enter special gesture state              |
| Exit gesture state       | write `0` to `0xD0`                 | none       | Exit special gesture state               |

## 10. Data Formats

## 10.1 Touch Coordinates

Each coordinate uses **12 bits**:

* `X = ((XH & 0x0F) << 8) | XL`
* `Y = ((YH & 0x0F) << 8) | YL`

### Point 1

* X high nibble: `0x03[3:0]`
* X low byte: `0x04[7:0]`
* Y high nibble: `0x05[3:0]`
* Y low byte: `0x06[7:0]`
* event flag: `0x03[7:6]`
* touch ID: `0x05[7:4]`

### Point 2

* X high nibble: `0x09[3:0]`
* X low byte: `0x0A[7:0]`
* Y high nibble: `0x0B[3:0]`
* Y low byte: `0x0C[7:0]`
* event flag: `0x09[7:6]`
* touch ID: `0x0B[7:4]`

## 10.2 Threshold/Formulas

* `ID_G_THGROUP (0x80)`: touch threshold = register value `/ 16`
* `ID_G_THDIFF (0x85)`: approximately `RV_G_THDIFF / 16`
* `ID_G_VIRTUAL_KEY_THRES (0xA9)`: approximately `VIRTUAL_KEY_THRESHOLD / 40`
* `AFE_Sample_Cycle (0x0C)`: actual scan sample count = `(AFE_Sample_Cycle + 1) * 8`
* `NLC_THR (0x20)`: threshold = `NLC_THR << 2`
* `Vsync_Width (0x23–0x24)`: `Tvsync = Vsync_Width / adcclk`
* `Vsync_Front_Porch (0x25)`: `Tvfp = (Vsync_Front_Porch << 4) / adcclk`
* `Vsync_Back_Porch (0x26)`: `Tvbp = (Vsync_Back_Porch << 4) / adcclk`
* `Hsync_Offset1 (0x27)`: `Thsyncoff1 = (Hsync_Offset1 << 2) / adcclk`
* `Hsync_Offset2 (0x28)`: `Thsyncoff2 = (Hsync_Offset2 << 2) / adcclk`
* `Hsync_Offset3 (0x29)`: `Thsyncoff3 = (Hsync_Offset3 << 2) / adcclk`

## 10.3 Multi-byte Data Buffers

Factory stream buffers use **2 bytes per channel** for RawData / CB / RS test data.

The workbook does not define byte endianness beyond stating 2 bytes per channel. Generated code should preserve raw byte ordering and allow platform-specific interpretation if later validated.

## 11. Timing Requirements

Only timing parameters explicitly defined in the register workbook are included.

## 11.1 Monitor Entry Delay

* `ID_G_TIMEENTERMONITOR (0x87)`
* units: **seconds**
* range: `0x00` to `0x64`
* reset: `0x1E`
* meaning: enter monitor state after the specified no-touch interval, if monitor mode is enabled

## 11.2 Scan Period Registers

* `ID_G_PERIODACTIVE (0x88)`: work mode scan period, range `0x04`..`0x14`, reset `0x08`
* `ID_G_PERIODMONITOR (0x89)`: monitor mode scan period, range `0x04`..`0x14`, reset `0x08`

## 11.3 SSCG Delay

* `SSCG_Delay (0x2C)`

  * `0x00 = 5us`
  * `0x01 = 10us`
  * `0x02 = 15us`
  * `0x03 = 20us`

## 11.4 Sync Timing Formulas

* `Tvsync = Vsync_Width / adcclk`
* `Tvfp = (Vsync_Front_Porch << 4) / adcclk`
* `Tvbp = (Vsync_Back_Porch << 4) / adcclk`
* `Thsyncoff1 = (Hsync_Offset1 << 2) / adcclk`
* `Thsyncoff2 = (Hsync_Offset2 << 2) / adcclk`
* `Thsyncoff3 = (Hsync_Offset3 << 2) / adcclk`

No additional startup, reset pulse width, wake latency, or conversion-complete timing is specified in the provided material.

## 16. Operational Sequences

## 16.1 Read Touch Points

1. Select work page by writing `0x00` to `0x00`.
2. Read `TD_STATUS` from `0x02`.
3. If touch count >= 1:

   * read `0x03`..`0x08`
   * reconstruct point 1 X/Y
4. If touch count >= 2:

   * read `0x09`..`0x0E`
   * reconstruct point 2 X/Y

## 16.2 Configure Monitor Behavior

1. Write monitor permission to `0x86`
2. Write no-touch timeout seconds to `0x87`
3. Write active scan period to `0x88`
4. Write monitor scan period to `0x89`
5. Optionally switch power mode via `0xA5`

## 16.3 Configure Gesture Mode

1. Write `1` to `0xD0` to enter gesture state
2. Program gesture enable bits in `0xD1`, `0xD2`, `0xD5`, `0xD6`, `0xD7`, `0xD8`
3. Read `0xD3` to obtain detected gesture ID
4. Write `0` to `0xD0` to exit gesture state when no longer needed

## 16.4 Read Factory Channel Order

1. Select factory page with `0x00 <- 0x40`
2. Read `TP_Channel_Num (0x0A)` and `TP_Key_Num (0x0B)`
3. Write start index to `0x31`
4. Read `0x37` for `channel_count + key_count` bytes

## 16.5 Read Factory Raw Data

1. Select factory page
2. Poll `0x08` until value `0x00`
3. Read `TP_Channel_Num` and `TP_Key_Num`
4. Set start index in `0x34`
5. Read `0x35` for `2 * N` bytes, where `N = channel_count + key_count`
6. Treat final extra close-mode bytes as documented

## 16.6 Read Factory CB Data

1. Select factory page
2. Read `TP_Channel_Num` and `TP_Key_Num`
3. Set start index in `0x33`
4. Read `0x39` for `2 * N` bytes

## 16.7 Read RS Test Data

1. Select factory page
2. Enable RS mode if needed via `0x07`
3. Set start index using `0x34`
4. Read `0xF4` for `2 * N` bytes

## 17. Driver Initialization Sequence

Recommended startup sequence:

1. Select **Work Mode page** by writing `0x00` to `0x00`.
2. Read and validate:

   * `0xA8` vendor ID
   * `0x9F`, `0xA0`, `0xA3` chip code bytes
   * `0xA6` firmware version
3. Program optional runtime settings only after ID validation:

   * `0x80` threshold
   * `0x85` filter threshold
   * `0x86` monitor enable
   * `0x87` monitor entry delay
   * `0x88` active period
   * `0x89` monitor period
   * `0xA4` interrupt mode
   * `0xA5` power mode
4. If gesture support is needed:

   * configure `0xD0`..`0xD8`
5. If factory diagnostics are needed:

   * switch to factory page only temporarily
   * perform factory accesses
   * switch back to work page

---

## 18. Runtime Operation Sequences

## 18.1 Polling-Based Touch Read

1. Read `0x02`
2. If `0`, no active points
3. Else parse touch records
4. Publish points with:

   * touch ID
   * event flag
   * X/Y coordinate
   * weight/misc raw bytes if needed

## 18.2 Update Thresholds

1. Read current register value if preserving reserved bits is required
2. Write new value to:

   * `0x80` touch threshold
   * `0x85` point filter threshold
   * `0xA9` virtual key threshold

## 18.3 Enter Low Power / Monitor

1. Set `0x86 = 0x01` if monitor allowed
2. Program `0x87`, `0x89`
3. Set `0xA5` to desired power mode

## 18.4 Charger Plug State Update

When host detects charger insertion/removal:

* write `0x8B = 0x01` for plug in
* write `0x8B = 0x00` for plug out

## 18.5 Upgrade Trigger

* write `0xAA`, then `0x55` to `0xBC`

## 19. Driver State Model

Driver should track at minimum:

* current page selection:

  * work
  * factory
* validated chip identity:

  * vendor ID
  * chip code bytes
  * firmware ID
* configured thresholds:

  * touch threshold
  * filter threshold
  * virtual key threshold
* current power mode
* monitor mode enable state
* scan periods
* gesture mode enable state
* enabled gesture masks
* last observed touch IDs and coordinates
* optional factory/test mode state when diagnostics are active

## 20. Required Safety and Correctness Rules for Code Generation

1. Always select the intended register page before any page-dependent access.
2. Do not assume the same address means the same function across work and factory pages.
3. Preserve reserved bits during read-modify-write unless writing a documented full-register command value.
4. Do not write reserved registers.
5. Validate chip identity before applying family-specific behavior.
6. Do not read touch point 2 registers unless `TD_STATUS` indicates at least 2 points.
7. Reconstruct coordinates as 12-bit values using high nibble + low byte.
8. Do not interpret undocumented event-flag encodings beyond carrying the raw field unless separately validated.
9. Treat `P1_WEIGHT`, `P1_MISC`, `P2_WEIGHT`, and `P2_MISC` as raw bytes unless higher-level meaning is validated.
10. Use `AcmdREG` readiness semantics before consuming RAWDATA in factory mode.
11. For factory stream buffers, size transfers using `TP_Channel_Num + TP_Key_Num`.
12. Treat RawData / CB / RS stream entries as 2 bytes per channel.
13. Do not assume undocumented byte endianness for streamed 2-byte channel data; expose raw bytes or configurable decode.
14. Use exact enumerated values for `ID_G_PMODE`, `Work_Mode`, and `ID_G_FACTORY_MODE`.
15. Use exact write sequence `0xAA`, `0x55` to `0xBC` for upgrade trigger.
16. Do not leave the device in factory page unless intentionally performing diagnostics.
17. When enabling gestures, program both global gesture-state enable (`0xD0`) and per-gesture enable bits.
18. Monitor entry delay register `0x87` is in seconds.
19. For threshold and timing-related registers, preserve exact formulas specified by the register definitions.
20. Where the workbook provides no electrical/bus timing, generated code must not invent delays or bus limits as hard requirements.

## 24. Minimal Functional Feature Set

A minimally correct driver implementation must support:

1. page switching through register `0x00`
2. device identification reads
3. reading `TD_STATUS`
4. reading and decoding up to 2 touch points
5. power mode configuration through `0xA5`
6. threshold configuration through `0x80` and `0x85`
7. interrupt mode configuration through `0xA4`
8. monitor mode configuration through `0x86`..`0x89`
9. safe handling of reserved bits/registers
10. optional factory-mode diagnostic access with correct page selection

---

## 25. Final Implementation Intent

A generated driver should behave as a robust register-transport adapter around a two-page FT6336-family control interface.

It should:

* correctly switch between work and factory pages
* validate device identity before applying advanced configuration
* decode touch-point reports into stable software-visible structures
* expose raw gesture, weight, misc, and factory diagnostic data without inventing semantics
* preserve reserved bits and avoid reserved-register writes
* use exact enumerated values and formulas from the register interface

Common implementation mistakes to avoid:

* forgetting page selection before register access
* treating `0xAE` identically in work and factory pages without regard to page context
* mis-decoding 12-bit X/Y values
* reading point-2 registers when only 1 point is reported
* overwriting reserved bits in single-bit control registers
* assuming undocumented physical bus timing or slave address
* assuming undocumented endianness for factory streamed 2-byte values
* leaving the device in factory mode after diagnostics
* enabling gesture masks without enabling gesture state via `0xD0`
* ignoring the RAWDATA-ready handshake in `AcmdREG`
